# Code review

Every change to `main` goes through a pull request and at least one review. The point is not
gatekeeping; it is a second pair of eyes on the things that are easy to get wrong in this
repository, most of which are listed below.

## Size

Aim for pull requests under roughly 400 changed lines, excluding generated files, message
bundles and migrations. Larger changes get a shallower review. If a task is bigger, split it:
a migration PR first, then the code that uses it; a refactoring PR first, then the feature.
Draft PRs are fine for early feedback on direction.

## What the reviewer checks

Correctness and design come first, but the project-specific list is where review earns its
keep. Go through it every time:

- [ ] The change does what the ticket asks, and nothing beyond it.
- [ ] Tests exist for new logic and for every new entry point (GraphQL field, admin route,
      RabbitMQ consumer). See [testing conventions](../conventions/testing.md).
- [ ] A migration, if any, was generated by `liquibase:diff` **and reviewed by hand**: PostGIS
      typmods, array columns, naming, indexes, backfill of `NOT NULL` columns. See
      [database changes](database-changes.md).
- [ ] Entity changes were made in `DB-Postgres` **and** in every service that carries a copy of
      that entity (`Admin-API`, `Client-API`, `Worker`). A diff that touches one copy
      and not the others is a bug waiting for `ddl-auto: validate`.
- [ ] Every new message key is present in all five bundles (`messages.properties`, `_uk`,
      `_pl`, `_de`, `_fr`) and `MessagesTest` is green.
- [ ] A new module is in the `Dockerfile` `COPY` list, in `docker-compose.services.yml`, and in
      both Prometheus configs. See [add a module](../extending/add-a-module.md).
- [ ] No secrets or personal API keys in code or configuration. Local defaults in
      `application.yaml` are fine; anything real goes through environment variables.
- [ ] Follows the [conventions](../conventions/README.md): records for data, Lombok only on
      entities and forms, `@Slf4j` where the module has Lombok, versions only in the root `pom.xml`, blocking code with
      virtual threads rather than WebFlux.
- [ ] Documentation is updated: the feature page in `features/`, the checklist in `extending/`
      if a procedure changed, the module page, and `.claude/CLAUDE.md` if a rule changed.
- [ ] Impact on the `Web-Client` is called out in the PR description when the GraphQL schema
      or the files route changed.

## How to comment

Mark what kind of comment it is so the author knows what has to happen before merge:

- **blocking**: a defect, a missing test, a broken convention, a security problem. Must be
  resolved or explicitly agreed otherwise.
- **question**: you do not understand why; the answer may end up as a code comment or a doc.
- **nit**: style or wording; the author may take it or leave it.

Comment on the code, not the person. Suggest a fix when you can; a one-line suggestion is
faster for everyone than a paragraph describing it. If the review turns into a design
discussion, take it to a call and write the outcome back on the PR.

## What the author does

- Self-review the diff on GitHub before requesting review. Most trivial findings disappear here.
- Make sure `./mvnw test-compile` and `./mvnw test` pass with Docker running. Run the `tests`
  workflow on the branch (module suites without `Admin-API`, then the integration tests); a red
  run is fixed before review, not explained.
- Fill in the PR template honestly, especially "How to test" and the migration/Keycloak/
  Web-Client sections. See [pull requests](../developer-guide/pull-requests.md).
- Respond to every comment, even with "done". Resolve the conversation yourself once addressed.
- Push fixes as new commits during review so the reviewer can see what changed; squash at merge.

## Approval and merge

- At least one approval from another developer. Changes to migrations, security configuration
  or the Keycloak realm should be reviewed by someone who has worked in that area.
- The **author** merges after approval, once the branch is up to date with `main`.
- Squash merge by default so `main` stays one commit per change. Rebase merge is fine when the
  commits are deliberately separate and each one builds.
- Delete the branch after merging.
- A migration PR is merged first and applied to the shared environments before the code that
  depends on it is deployed. See [release](release.md).

## Turnaround

A review request should get a first response within one working day. If you cannot get to it,
say so and hand it over. Blocked PRs rot: the author should ping after a day of silence.
