# Internationalization

The admin panel is rendered in five languages and every string the user can see comes from a message bundle. How locale selection works end to end is described in [localization](../features/localization.md); adding a sixth language is in [add-a-language](../extending/add-a-language.md). This page is what a change to the UI must respect.

## Bundles

```
Admin-API/src/main/resources/
  messages.properties       # English, also the fallback
  messages_uk.properties
  messages_pl.properties
  messages_de.properties
  messages_fr.properties
```

`spring.messages.fallback-to-system-locale: false`, so an unknown locale lands on `messages.properties`, never on the machine's locale. The supported locales are the list `LocaleConfig.SUPPORTED`; the current one comes from the `DERECHI_LOCALE` cookie and is switched with `?lang=xx`.

## Rules

**No literal text in templates.** Every visible string is `#{key}` (or `th:text="#{...}"`, `th:placeholder`, `th:title`, `th:data-error`). A literal placed in the template "just for now" shows up in English for Ukrainian users and is not caught by anything.

```html
<!-- bad -->
<button class="button">Notify</button>

<!-- good -->
<button class="button" th:text="#{matches.notify}">Notify</button>
```

The English text inside the tag is fine as a visual placeholder for the designer; Thymeleaf replaces it.

**A new key goes into all five files.** `MessagesTest` loads the base bundle and every `messages_xx.properties` from `LocaleConfig.SUPPORTED` and fails when a key is missing in any of them or when the set of `{0}`, `{1,number}` placeholders differs between translations. A translation you cannot write yet still goes in, in English, so the build stays green and the gap is visible in the file rather than on screen.

**Message format is always on.** `spring.messages.always-use-message-format: true` means every message is parsed by `MessageFormat`, with or without arguments. A single quote must therefore be doubled (`l''objet`) and literal braces escaped (`'{'`). Forgetting this silently eats the quote.

**Plurals go through `Plurals`.** `MessageFormat`'s choice format cannot express Slavic plural rules (one, few, many). `Plurals` picks the category for the current locale (three forms for `uk`, `pl`, `ru`, `be`; zero counts as singular in `fr`; `one`/`other` elsewhere) and resolves `key.one`, `key.few`, `key.many`, `key.other`, falling back to `.other`:

```properties
list.records.one={0} record
list.records.few={0} records
list.records.many={0} records
list.records.other={0} records
```

```html
<span th:text="${plural.records(items.totalElements)}">0 records</span>
```

For a new countable thing add the four keys in every bundle and call `${plural.format('your.key', count)}`.

**Dates, money, phones and country names go through `Formats`.** It is exposed to templates as `${fmt}` by `GlobalModelAdvice`:

| Call | Output |
|---|---|
| `${fmt.date(item.date)}` | locale-formatted date |
| `${fmt.money(item.compensation, item.currency)}` | amount with the ISO 4217 currency, no conversion |
| `${fmt.country(item.countryCode)}` | country display name from the JDK for the current locale, so a new country needs no bundle key |
| `${fmt.phone(info.phone)}` | international format via libphonenumber |
| `${fmt.dateTime(claim.createdAt)}` | medium date and short time of an `Instant`, in the server's time zone |

Do not format any of these with `#dates`, `#numbers` or string concatenation in a template.

**Exceptions carry keys.** `NotFoundException("entity.LOST_ITEM", id)` stores the entity key; `GlobalExceptionHandler` resolves `entity.LOST_ITEM` in the current locale and builds the message. `RejectedUploadException("upload.tooLarge")` is resolved the same way in `UploadController`. A new exception type that reaches the user follows the pattern: key in, text out at the edge.

**Validation messages use the same bundles.** `LocaleConfig` registers a `LocalValidatorFactoryBean` bound to the application `MessageSource`, so a constraint on `ItemForm` with `message = "{validation.something}"` and an `errors.rejectValue("countryCode", "validation.country")` in `ItemFormValidator` both resolve from `messages*.properties` (`validation.phone`, `validation.country`, `validation.currency` exist today). Do not create a separate `ValidationMessages.properties`.

**Notification texts are localized too.** `MatchNotificationService` builds the e-mail subject and body from `notification.match.subject` and `notification.match.body` in the admin's current locale. A change to the notification wording is a bundle change.

## Key naming

Dotted, lower camel inside segments, grouped by screen or concept: `nav.*`, `page.*`, `entity.*`, `action.*`, `list.*`, `form.*`, `validation.*`, `matches.*`, `upload.*`, `notification.*`. Keys are stable identifiers; rename only when the meaning changes, because a rename touches five files and the templates.

## Web client

`Web-Client` has its own bundles in `Web-Client/messages/*.json` for the same five locales, shares the `DERECHI_LOCALE` cookie and has its own parity test (`pnpm test`). A user-facing text on the public site is changed there, not in the Spring bundles; the two sets are independent. Backend changes that affect the web client are only announced, not applied, from the Java side.
