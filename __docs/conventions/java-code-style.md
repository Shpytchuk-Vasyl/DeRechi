# Java code style

Java 26, Spring Boot 4.1. The rules below are what reviewers check for. See [testing](testing.md) for what a change must ship with and [maven-and-modules](maven-and-modules.md) for build layout.

## Data is a `record`, state is a class with Lombok

Anything that only carries values is a record: DTOs, views, filters, projections, events that are not mutated, and configuration properties.

```java
public record MatchRow(ItemView lost, List<CandidateView> candidates, long total) {}
public record CandidateCount(Long lostItemId, long total) {}
public record ItemFilter(String q, Long categoryId, LocalDate from, LocalDate to) { ... }
```

Examples in the tree: `ItemView`, `ItemFilter`, `MatchRow`, `CandidateCount`, `NotifiedMatch`, `SortView` in `Admin-API`, every `*Dto` and `*Input` in `Client-API`, `NotificationRequestedEvent` in `Notification`.

Records need `-parameters` to work with Jackson, `@Argument` in GraphQL and constructor binding in `@ConfigurationProperties`. The root `maven-compiler-plugin` sets it; do not override the compiler plugin in a module without keeping it.

Lombok is used only where setters and a no-args constructor are unavoidable: JPA entities and Spring MVC form objects.

```java
@Entity
@Getter
@Setter
@NoArgsConstructor
public class Place { ... }
```

Services and controllers take their collaborators through the constructor, generated by `@AllArgsConstructor`:

```java
@Service
@AllArgsConstructor
public class MatchService { private final LostItemRepository lostItemRepository; ... }
```

Do not put `@Data`, `@Builder` or `@Value` on anything. `@Data` generates `equals`/`hashCode` over all fields, which is wrong for entities and unnecessary for records.

Lombok is declared with `provided` + `optional` scope and listed in `annotationProcessorPaths` only in `Admin-API`, `Client-API` and `Worker`. Modules without Lombok (`Notification`, `Getaway`, `Discovery`) stay without it.

## Logging

Always a static logger from `LoggerFactory`:

```java
private static final Logger log = LoggerFactory.getLogger(MatchService.class);
```

`@Slf4j` is not used in this project. One style keeps the codebase greppable and the logger field visible where it is declared.

Log with placeholders, never string concatenation. Do not log full stack traces for expected conditions (a missing entity, a validation failure); those are handled and rendered by `GlobalExceptionHandler` or `GraphQlExceptionResolver`.

## Blocking code, virtual threads

Every servlet module runs with `spring.threads.virtual.enabled: true`. Write plain blocking code: JPA repositories, `RabbitTemplate`, and `RestClient` for any outbound HTTP you need. Do not introduce WebFlux, `WebClient` or `RestTemplate` into these modules. The only reactive module is `Getaway`, because Spring Cloud Gateway is built on WebFlux.

## Configuration properties

Bind typed configuration to a record under the `derechi.*` prefix and validate in the compact constructor, so a bad value fails the application at startup rather than on the first request:

```java
@ConfigurationProperties(prefix = "derechi.countries")
public record CountriesProperties(List<String> supported, String fallback) {
    public CountriesProperties {
        if (supported == null || supported.isEmpty()) {
            throw new IllegalArgumentException("derechi.countries.supported must not be empty");
        }
        ...
    }
}
```

Enable it with `@EnableConfigurationProperties(...)` on the `@Configuration` that uses it (`CountriesConfig`, `StorageConfig`, `MapsConfig`, `SecurityConfig`). Do not read `@Value("${...}")` strings in services.

## Exceptions and messages

`Admin-API` renders every error page in the user's language, so exceptions carry a message **key**, not text:

```java
throw new NotFoundException("entity.LOST_ITEM", id);   // key resolved in GlobalExceptionHandler
throw new RejectedUploadException("upload.tooLarge"); // key resolved in UploadController
```

`Client-API` is a GraphQL API for programmatic clients and uses plain English messages mapped to GraphQL error types by `GraphQlExceptionResolver`: `NotFoundException` to `NOT_FOUND`, `IllegalArgumentException` and `ConstraintViolationException` to `BAD_REQUEST`. Keep the wording stable (`Unsupported country: XX`, `Unsupported currency: XXX`), the web client may match on it.

## Nullability

Use JSpecify `org.jspecify.annotations.Nullable` and `NonNull` on record components, parameters and return types where null is part of the contract (see `NotificationRequestedEvent` and `NotifyChannel#social()`). The default is non-null; annotate the exceptions, not the rule.

## Persistence

- `spring.jpa.open-in-view: false` in every module. Load what the view needs inside the service, usually with a `findWithDetailsById`-style query or an entity graph, and map it to a record before leaving the transaction.
- Read-only service methods are `@Transactional(readOnly = true)`, writers are `@Transactional`. Controllers are never transactional.
- `ddl-auto: none` everywhere except `DB-Postgres` (`validate`) and tests. Services never run Liquibase; see [database-migrations](database-migrations.md).
- Dynamic queries go through `Specification`s in a `*Specifications` final class with a private constructor and static factory methods.
- Sorting coming from the request must pass through `Pages.safe(...)`, which keeps only `id`, `title` and `date`. Without the whitelist any entity field ends up in `order by`.

### Entities copied per module

Entities live in `DB-Postgres` for migrations and are **copied** into each service that needs them (`org.shpytchuk.adminapi.entity`, `...clientapi.entity`, `...worker.entity`). No module depends on `DB-Postgres`. That means:

- A mapping change is made in `DB-Postgres` first, then mirrored in every copy. Table and column names, nullability, lengths and `@JdbcTypeCode` must stay identical; tests run with `ddl-auto: validate` against the real changelog and will fail on drift, but only in the modules that have such tests.
- A service copy may omit fields and relations it does not read (`Notification` has no entities at all), but it must not rename or retype anything it keeps. `Worker` carries the history and claim entities because it archives notices.
- `ContactInfo.SocialMediaEnum` is stored as an ordinal array (`smallint[]`). Enum constants may only be **appended**; reordering or inserting changes the meaning of every stored row.

## Constants

Routing keys, exchange names, base paths and message keys are `static final` constants on the class that owns them, and public when another class needs them:

```java
static final String BASE_PATH = "/admin/matches";
private static final String ROUTING_KEY = "item.found.created";
private static final String SUBJECT_KEY = "notification.match.subject";
```

Routing keys are duplicated between publisher and consumer on purpose (the modules share no code), so a change must be made on both sides and in `docker/rabbitmq/definitions.json`. See [messaging](../architecture/messaging.md).

## Naming

| Thing | Pattern | Examples |
|---|---|---|
| MVC controller | `*Controller` | `LostItemController`, `MatchController` |
| Admin service | `*AdminService` (CRUD) or `*Service` | `LostItemAdminService`, `MatchNotificationService` |
| Repository | `*Repository` | `SimilarItemRepository` |
| Specifications | `*Specifications` | `ThingSpecifications` |
| Typed config | `*Properties` | `StorageProperties` |
| Template model | `*View`, `*Row` | `ItemView`, `MatchRow`, `CandidateView` |
| MVC form | `*Form`, `*Filter` | `ItemForm`, `ItemFilter` |
| GraphQL input / output | `*Input` / `*Dto` | `PlaceInput`, `ItemDto` |
| RabbitMQ event | `*Event` with `@EventType("...")` | `ItemCreatedEvent` |
| RabbitMQ consumer | `*Listener` | `ItemCreatedListener` |
| Test | `*Test` (unit), `*Tests` (Spring slice/integration), `*IT` (needs running infra) | `FormatsTest`, `MatchControllerTests`, `ImageStorageIT` |

Classes are singular nouns; a class that exists only for static helpers is `final` with a private constructor (`Pages`, `Permissions`, `ContactMasker`, `GeoPoints`).

## Package layout

Each service follows the same shape under `org.shpytchuk.<module>`:

```
config/        @Configuration classes, properties records, interceptors
controller/    MVC or GraphQL controllers
model/         Admin-API only: @ControllerAdvice and the model helpers templates rely on
entity/        JPA entities, copied from DB-Postgres
event/         @EventType records/classes, EventTypeScanner
form/ input/   request-side objects (MVC forms, GraphQL inputs)
dto/ view/     response-side records
mapper/        static entity-to-record mappers
repository/    Spring Data repositories and *Specifications
security/      Admin-API only: Scope, Action, Permissions, mappers
service/       business logic
listener/      RabbitMQ consumers (Worker, Notification)
handler/       Worker only: one handler per routing key, picked by the listeners
cron/          Worker only: @Scheduled jobs
util/          pure static helpers
```

Inside `entity`, `repository`, `service` and `view` the classes are split by the thing they
are about, the same way in every module: `lost/` and `found/` for the notice kind and
everything that hangs off it (item, history, claim), `thing/` for the shared `Thing` and its
category, `detail/` for `ContactInfo` and `Place`, `matching/` for `SimilarItem`, `Claim` and
the match views. A class that serves both kinds (`ItemService`, `ClaimRepository`,
`AdminItemService`) stays at the package root. Keep new code in these packages rather than
adding new top-level ones.

## Comments

Code comments and Javadoc explain a non-obvious decision, not what the next line does. Mixed-language comments exist in the tree today; new comments are written in English so the docs and the code agree.
